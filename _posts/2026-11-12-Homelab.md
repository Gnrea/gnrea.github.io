Overview
Four Proxmox nodes (HomeLab, Laptop, MiniLab-1, MiniLab-2) in one cluster, with Tailscale for remote access. Each service gets its own Debian VM so it can be snapshotted, rebuilt or deleted on its own.

VM	Node	Job
NAS VM	HomeLab	Samba file shares, Immich (Docker), Tailscale
Vaultwarden VM	Laptop	Password manager (Docker), Tailscale HTTPS
Jellyfin VM	Laptop	Media server (Docker), mounts NAS share read-only
Pi-hole VM	Laptop	DNS ad blocking, used per device
Placeholders used below:

<NAS_LAN_IP>: the NAS VM's LAN address (give it a DHCP reservation)
<TAILNET>: your tailnet name (<machine>.<TAILNET>.ts.net)
youruser: your normal Linux user
MY NOTES:

Part 1: Proxmox hosts (HomeLab and Laptop)
The problem
A default Proxmox install on a 1 TB disk gives root about 100 GB and puts the rest in a data thin pool (local-lvm). I wanted a much bigger local for ISOs and files, and a smaller thin pool for VM disks.

Check before deleting anything
bash
lsblk
vgs
lvs -a
pvesm status
# Confirm no VM config references an LV in the pool:
grep -H "vm-\|local" /etc/pve/nodes/*/qemu-server/*.conf
# Confirm root is ext4:
findmnt /
In my case the pool was nearly empty (about 2% used) and every VM disk was a qcow2 file on local, so the thin pool held only orphaned LVs.

Rebuild the layout
bash
# WARNING: destroys everything inside the thin pool
lvremove pve/data

# Grow root and its ext4 filesystem online (-r resizes the filesystem too)
lvextend -r -L 480G pve/root

# Recreate a smaller thin pool, with explicit metadata size
lvcreate --type thin-pool -L 430G --poolmetadatasize 4G -n data pve

lvs -a
vgs
df -h /
On the Laptop node (slightly different swap size) I used a 420G pool.

Register the pool in Proxmox
Datacenter → Storage → Add → LVM-Thin

ID: any name (one per node, for example local-lvm and local-lvm-laptop)
Volume group: pve
Thin pool: data
Content: Disk image, Container
Nodes: restrict to the one node that owns the pool
Gotchas
The web UI shows decimal GB. LVM works in GiB. A "1 TB" disk is about 930 GiB, so my first lvcreate failed with "insufficient free space".
A fully allocated volume group shows red 100% in Disks → LVM. That only means everything is handed out, not that the disk is full.
ISO storage only lists directory storages. The thin pool never shows up in the ISO dropdown.
Shrinking root later needs a live USB (ext4 can't shrink while mounted). I decided not to do that remotely.
A thin pool at 100% can corrupt the VMs on it. Watch Data% under Disks → LVM-Thin.

Part 2: NAS VM (HomeLab)
VM settings
Setting	Value
Machine / BIOS	q35 / SeaBIOS (no EFI disk needed)
SCSI controller	VirtIO SCSI single, IO thread on
Disk 1 (OS)	20 GiB, thin pool, Discard on, Cache: No cache
Disk 2 (data)	350 GiB, thin pool, Discard on
CPU	1 socket, 3 cores, type host
RAM	5120 MiB, ballooning off
Network	VirtIO, vmbr0, no VLAN tag
Options	Start at boot on, QEMU Guest Agent on
I left about 4 GiB of the volume group unallocated as a safety buffer.

Install Debian
Debian 12, graphical installer, "Guided - use entire disk" on the 20 GB disk only, "All files in one partition". Software selection: untick every desktop, tick only SSH server and standard system utilities. Choose a network mirror.

First boot (console, as root)
bash
apt update && apt full-upgrade -y
apt install -y sudo curl ca-certificates qemu-guest-agent samba
usermod -aG sudo youruser      # NOT chgrp: usermod changes a user's groups
Log out and SSH back in as youruser. Root cannot log in over SSH by default on Debian.

Format and mount the data disk
bash
lsblk                          # confirm the 350G disk (sdb) BEFORE running anything
sudo fdisk /dev/sdb            # g, n, Enter x3, w
sudo mkfs.ext4 /dev/sdb1
sudo mkdir -p /srv/nas
sudo blkid /dev/sdb1           # copy the UUID
sudo nano /etc/fstab
Add this line to /etc/fstab:

UUID=<uuid-from-blkid>  /srv/nas  ext4  defaults,nofail  0  2
bash
sudo systemctl daemon-reload
sudo mount -a
df -h /srv/nas                 # must show the big disk, not the 20G OS disk
defaults is the normal read/write bundle. nofail lets the VM boot even if the disk is missing. The catch: if the mount fails, /srv/nas is just an empty folder on the OS disk, so check df -h /srv/nas after reboots.

Folders, users and Samba
bash
sudo mkdir -p /srv/nas/isos /srv/nas/files /srv/nas/media
sudo groupadd nasusers
sudo useradd -M -s /usr/sbin/nologin -G nasusers nasuser
sudo smbpasswd -a nasuser
sudo chown -R root:nasusers /srv/nas
sudo chmod -R 2775 /srv/nas    # 2 = setgid, new files inherit the group
sudo cp /etc/samba/smb.conf /etc/samba/smb.conf.bak
sudo nano /etc/samba/smb.conf
Append to smb.conf:

ini
[isos]
   path = /srv/nas/isos
   valid users = nasuser
   read only = yes

[files]
   path = /srv/nas/files
   valid users = @nasusers
   read only = no
   create mask = 0664
   directory mask = 2775
Recommended under [global]:

ini
hosts allow = 192.168.x. 100.64.0.0/10 127.
hosts deny = ALL
bash
testparm
sudo systemctl restart smbd
Test from Windows at \\<NAS_LAN_IP>\files.

Remote access with Tailscale
bash
curl -fsSL https://tailscale.com/install.sh | sh
sudo tailscale up
tailscale ip -4
tailscale status               # look for "direct", not "relay"
In the Tailscale admin console, disable key expiry for the machine. Keep Proxmox's own mounts of the share on the LAN IP, not the Tailscale IP.

Docker (official repo, deb822 format)
bash
sudo apt remove docker.io docker-compose docker-doc podman-docker containerd runc
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/debian/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

sudo tee /etc/apt/sources.list.d/docker.sources <<EOF
Types: deb
URIs: https://download.docker.com/linux/debian
Suites: $(. /etc/os-release && echo "$VERSION_CODENAME")
Components: stable
Signed-By: /etc/apt/keyrings/docker.asc
EOF

sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-compose-plugin
sudo docker run hello-world
Always compare the repo block with https://docs.docker.com/engine/install/debian/. I did not add my user to the docker group because that group is effectively root, so every command uses sudo.

Immich (Docker Compose)
bash
sudo mkdir -p /opt/immich /srv/nas/media/immich /srv/nas/immich-db
cd /opt/immich
sudo wget -O docker-compose.yml https://github.com/immich-app/immich/releases/latest/download/docker-compose.yml
sudo wget -O .env https://github.com/immich-app/immich/releases/latest/download/example.env
sudo nano .env
Values changed in .env:

UPLOAD_LOCATION=/srv/nas/media/immich
DB_DATA_LOCATION=/srv/nas/immich-db
DB_PASSWORD=<strong-letters-and-numbers>
TZ=America/Chicago
Use a full IANA timezone name, not CST. Leave DB_USERNAME and DB_DATABASE_NAME at their defaults.

bash
sudo docker compose up -d
sudo docker compose ps
sudo docker compose logs --tail=30 immich-server
Then open http://<NAS_LAN_IP>:2283.

Setup choices I made:

First account becomes admin. Create a second admin as a backup.
Storage template: YYYY/MM/DD so photos stay browsable on disk without Immich.
Version check on; Google Cast off; map optional.
Face recognition is optional and runs locally in the immich-machine-learning container. Nothing leaves the server.
Phone app: server URL set to the NAS Tailscale address, Tailscale app on each phone.
Persistence: container filesystems are temporary, but the photo folder and database are bind mounts under /srv/nas, so they survive restarts and updates. Avoid docker compose down -v.

Updating Immich (read release notes first):

bash
cd /opt/immich
sudo docker compose pull
sudo docker compose up -d
Gotchas
cat on an image dumped binary into the terminal and garbled it. Fix with reset. Don't cat binaries.
mkfs warned that sdb1 already held an ext4 filesystem (the installer had touched it). It was empty, so I answered y.
The data disk is a single copy on a single disk. Backups are still on my to-do list.

Part 3: Vaultwarden VM (Laptop)
VM settings
1 core, 1024 MiB RAM (ballooning off), 20 GB disk (thin pool, Discard on), VirtIO, Start at boot on, QEMU Guest Agent on.

Problem: apt only knew about the install CD
I skipped the installer's mirror step, so /etc/apt/sources.list held a single deb cdrom: line and apt update failed. Network, DNS and clock were all fine. Fix (Debian 13 "trixie"), as root at the console:

bash
cp /etc/apt/sources.list /etc/apt/sources.list.bak
cat > /etc/apt/sources.list <<EOF
deb http://deb.debian.org/debian trixie main
deb http://deb.debian.org/debian trixie-updates main
deb http://security.debian.org/debian-security trixie-security main
EOF

apt update
apt install -y ca-certificates curl sudo qemu-guest-agent openssh-server
usermod -aG sudo youruser
systemctl enable --now ssh
http:// is fine for the first update because the packages are signed, and a minimal install has no ca-certificates yet. non-free-firmware is not needed inside a VM, and non-free does not cost money (it is a licensing label).

Install Docker and Tailscale
Same steps as the NAS VM (Docker deb822 repo, then Tailscale). In the Tailscale admin console, enable MagicDNS and HTTPS Certificates, and disable key expiry for this machine.

bash
tailscale status --json | grep -m1 DNSName    # your <machine>.<TAILNET>.ts.net name
Run Vaultwarden
bash
sudo mkdir -p /opt/vaultwarden/data
sudo chmod 700 /opt/vaultwarden/data
cd /opt/vaultwarden
sudo tee docker-compose.yml <<'EOF'
services:
  vaultwarden:
    image: vaultwarden/server:latest
    container_name: vaultwarden
    restart: unless-stopped
    environment:
      DOMAIN: "https://<machine>.<TAILNET>.ts.net"
      SIGNUPS_ALLOWED: "true"
    volumes:
      - ./data:/data
    ports:
      - "127.0.0.1:8080:80"
EOF

sudo docker compose up -d
sudo docker compose ps
curl -I http://127.0.0.1:8080          # expect HTTP 200
Binding to 127.0.0.1 means only the VM itself can reach the container. Tailscale Serve is the only way in.

HTTPS with Tailscale Serve
bash
sudo tailscale serve --bg 8080
tailscale serve status                 # shows the https:// URL
The Serve syntax has changed between Tailscale versions, so check tailscale serve --help and the Tailscale docs. The URL shown must match DOMAIN exactly. The Bitwarden apps need HTTPS.

Accounts and lock-down
Register your account with a long, unique master password (nobody can recover it).
Turn on two-step login and save the recovery code offline.
When family has registered, set SIGNUPS_ALLOWED: "false" and run sudo docker compose up -d again. Data stays in ./data.
Notes:

The registration email is just a username. A made-up address works because no SMTP server is configured, but that also means no emailed recovery.
Bitwarden clients keep an encrypted local copy, so reading passwords works offline.
Still to do

Keep an encrypted vault export somewhere that is not the NAS.

Part 4: Jellyfin VM (Laptop)
VM settings
2 cores (type host), 3072 to 4096 MiB RAM (ballooning off), 30 GB disk, Start at boot on, QEMU Guest Agent on. Debian installer: choose a network mirror, tick only SSH server and standard system utilities.

First boot and packages
bash
sudo apt update
sudo apt install -y curl ca-certificates qemu-guest-agent cifs-utils
cifs-utils provides the helper that lets Linux mount an SMB/Samba share from /etc/fstab. Then install Docker and Tailscale as above.

On the NAS VM: a read-only share for Jellyfin
I did not share /srv/nas/media, because Immich's library lives there. I used a separate folder and a dedicated read-only user.

bash
sudo mkdir -p /srv/nas/library/movies /srv/nas/library/shows /srv/nas/library/music
sudo chown -R root:nasusers /srv/nas/library
sudo chmod -R 2775 /srv/nas/library
sudo useradd -M -s /usr/sbin/nologin jfin
sudo smbpasswd -a jfin
sudo nano /etc/samba/smb.conf
ini
[library-ro]
   path = /srv/nas/library
   valid users = jfin
   read only = yes

# Writable share so I can copy media in from my PC
[library]
   path = /srv/nas/library
   valid users = @nasusers
   read only = no
   create mask = 0664
   directory mask = 2775
bash
testparm
sudo systemctl restart smbd
On the Jellyfin VM: mount the share
bash
sudo mkdir -p /mnt/library
sudo nano /root/.smbcredentials        # two lines: username=jfin / password=YOUR_PASSWORD
sudo chmod 600 /root/.smbcredentials
sudo nano /etc/fstab
One line in /etc/fstab:

//<NAS_LAN_IP>/library-ro  /mnt/library  cifs  credentials=/root/.smbcredentials,ro,file_mode=0444,dir_mode=0555,vers=3.0,_netdev,nofail,x-systemd.automount  0  0
bash
sudo systemctl daemon-reload
sudo mount -a
ls /mnt/library
I used the LAN IP, not the Tailscale IP. Both VMs are on the same LAN, it skips VPN overhead, and a Tailscale address may not be up yet at boot. Set a DHCP reservation for the NAS so the IP never changes. ro protects the media, nofail lets the VM boot without the NAS, and x-systemd.automount mounts on first access.

Run Jellyfin
bash
sudo mkdir -p /opt/jellyfin/config /opt/jellyfin/cache /opt/jellyfin/test
cd /opt/jellyfin
sudo tee docker-compose.yml <<'EOF'
services:
  jellyfin:
    image: jellyfin/jellyfin:latest
    container_name: jellyfin
    restart: unless-stopped
    ports:
      - "8096:8096"
    volumes:
      - ./config:/config
      - ./cache:/cache
      - /mnt/library:/media:ro
      - /opt/jellyfin/test:/test:ro
EOF

sudo docker compose up -d
sudo docker compose ps
Open http://<jellyfin-vm-ip>:8096 and run the setup wizard.

Test library
Free test media: the Blender open movies (Big Buck Bunny, Sintel, Tears of Steel) from blender.org, as 720p/1080p H.264 MP4. Folder naming that Jellyfin matches well:

/opt/jellyfin/test/movies/Big Buck Bunny (2008)/Big Buck Bunny (2008).mp4
bash
sudo chown -R $USER:$USER /opt/jellyfin/test
sudo chmod -R a+rX /opt/jellyfin/test     # the container reads as a different user
In Dashboard → Libraries → Add Media Library, the folder picker shows the container's paths (/test/movies, /media/movies), not the VM's host paths.

Notes
No GPU passthrough on this CPU (i5-6500TE, 4 threads), so I rely on direct play. MKV/MP4 with H.264/H.265 video and AAC audio direct-plays most places.
Jellyfin has a "Home Videos and Photos" library type, but it is only a basic viewer. Immich is the photo app, and I did not point Jellyfin at Immich's folder.
Back up /opt/jellyfin/config (users and watch history).

Part 5: Pi-hole VM (Laptop)
What Pi-hole actually is
Pi-hole is a DNS server, not a router. Only devices told to use it send it queries, so I can test it on one device without touching the rest of the network.

VM settings
1 core, 512 to 1024 MiB RAM, 8 to 10 GB disk, Debian minimal, fixed IP (DHCP reservation), Start at boot on.

Setup
bash
sudo apt install -y curl ca-certificates qemu-guest-agent
curl -sSL https://install.pi-hole.net | bash
sudo pihole setpassword
Native install rather than Docker: it is the only thing on the VM, it listens on port 53 and needs to see real client IPs, and Docker would add a NAT and firewall layer for no benefit. Check https://docs.pi-hole.net for current install steps.

Installer choices:

Upstream DNS: Quad9 (filtered, 9.9.9.9). Unfiltered is 9.9.9.10, and the ECS variant (9.9.9.11) shares part of your subnet with sites, so I skipped it. Confirm current addresses at quad9.net.
Privacy mode: Show everything while tuning, then move to a more private mode once stable (the log is a record of everyone's browsing).
Pi-hole's own DNSSEC option left off, since Quad9 validates DNSSEC.
Test on a single device
bash
nslookup doubleclick.net <pihole-ip>     # blocked domain returns 0.0.0.0 or similar
nslookup debian.org <pihole-ip>          # normal domain resolves
Then set DNS on just my PC to the Pi-hole IP and watch the query log. Do not switch the whole router's DNS until it has been stable for a while, because if the VM is down every device using it loses name resolution. Never forward port 53 on the router.

MY NOTES:

Lessons learned
Check the installer's mirror step. Skipping it leaves apt with only a CD source.
usermod -aG sudo user, not chgrp. Group changes only apply to new logins.
Debian blocks root over SSH. Log in as your normal user, then sudo.
Use UUIDs in /etc/fstab, and nofail on data disks. Verify with df -h after every reboot.
Keep containers off the LAN when you can (127.0.0.1: port bindings), and don't port-forward anything. Tailscale is the way in.
Thin provisioning is not free space. Watch the pool's Data%.
A NAS on one disk is one copy. Plan a second local copy (an external SSD or another machine) and an off-site copy before trusting it with irreplaceable files.
Services that share a VM share its failures. Separate VMs made each one easy to snapshot and rebuild.
Verify against official docs (docs.docker.com, docs.immich.app, the Vaultwarden wiki, docs.pi-hole.net, Tailscale KB), since flags, repo formats and menus change between releases.
